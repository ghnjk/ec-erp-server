## Context

`SkuDto` 已包含 `is_delete` 字段，但 `search_sku` 未过滤该字段，且 Supplier 模块没有删除 SKU 的接口。前端 SKU 列表也缺少高风险操作的二次确认。项目已有供应商和销售订单逻辑删除模式，可复用其事务与权限约定。

## Goals / Non-Goals

**Goals:**

- 在当前项目范围内按 SKU 逻辑删除主数据。
- 删除后立即从 SKU 列表隐藏，并允许通过批量添加恢复。
- 前端展示待删除 SKU 的上下文，并要求精确输入 SKU 二次确认。
- 保持真实 API、前端封装、Mock 与文档一致。

**Non-Goals:**

- 不物理删除 `t_sku_info` 行。
- 不级联删除采购价、采购单、销售订单等关联数据。
- 不删除 BigSeller/UpSeller 远端 SKU。
- 不把二次确认文本作为后端参数。

## Decisions

1. **复用 `Fis_delete` 进行逻辑删除。** 这与项目业务表惯例一致，可保留历史关联。物理删除虽然简单，但会破坏审计和潜在关联查询。
2. **后端以 `project_id + sku` 定位记录。** 所有查询和修改都经过当前项目 Backend，保证多项目隔离；删除不存在或已删除的 SKU 返回业务错误。
3. **`search_sku` 强制过滤 `is_delete == 0`。** 逻辑删除必须在默认列表查询中不可见，避免前端依赖额外过滤。
4. **重新添加恢复已删除记录。** 主键是 `project_id + sku`，不能插入重复行；`add_sku` 对已删除记录重新查询 ERP 信息并写入 `is_delete=0`。
5. **确认门槛放在前端交互层。** 对话框展示图片和基本信息，只有输入值与 SKU 完全一致时确认按钮才可用；后端仍只校验权威的 `sku` 参数和权限。
6. **操作列始终显示。** 将 `operation` 标记为必显并置于列定义末尾，避免列设置隐藏删除入口或改变“最后一列”的要求。

## Risks / Trade-offs

- [旧调用方依赖查询已删除数据] → `search_sku` 是业务列表接口，明确只提供有效数据；历史数据仍保留在数据库。
- [恢复时旧字段残留] → 使用现有新增流程重新获取 ERP 信息，并构造完整 `SkuDto` 显式写入 `is_delete=0`。
- [并发重复删除] → API 在删除前检查有效状态；事务内再次按项目和 SKU 更新，失败统一回滚。
- [误删] → Supplier 权限校验、危险色按钮、上下文展示和精确输入 SKU 四层约束。

## Migration Plan

1. 部署后端逻辑删除、查询过滤和恢复逻辑。
2. 部署前端 API、Mock 和确认对话框。
3. 无数据库迁移；`Fis_delete` 已存在。
4. 回滚代码即可恢复旧行为，已标记删除的数据可手工将 `Fis_delete` 改回 0。
